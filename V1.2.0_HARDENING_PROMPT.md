## WAVE U: WebAuthn Phone Enrollment — End-to-End

**Goal:** Replace the DB-level `UPDATE pending_sessions SET status='approved'`
shortcut with a real WebAuthn enrollment + assertion flow that a phone (via
ntfy + browser) can actually perform.

**Context budget:** 4 sub-agent tasks, each ≤ 500 lines of code change.

### U1 (sub-agent): WebAuthn ceremony generation
- **File:** `gateway/src/crypto/webauthn.rs` + `gateway/src/routes/phone.rs`
- **Task:** Implement `generate_ceremony_options(tenant_id) → PublicKeyCredentialCreationOptions` and `POST /phone/ceremony/begin` that returns the CBOR-encoded options. Store the challenge in `phone_challenges` table (new migration 005).
- **DoD:**
  - `POST /phone/ceremony/begin?tenant=<id>` returns valid `PublicKeyCredentialCreationOptions` JSON with `challenge`, `rp`, `user`, `pubKeyCredParams` (ES256 + RS256).
  - Challenge is 32 random bytes, base64url-encoded.
  - `phone_challenges` table has `id`, `tenant_id`, `challenge`, `created_at`, `used_at`.
  - Unit test: `test_ceremony_options_shape`.
- **Commit:** `feat(webauthn): generate enrollment ceremony options + /phone/ceremony/begin`

### U2 (sub-agent): WebAuthn assertion verification (real)
- **File:** `gateway/src/crypto/webauthn.rs`
- **Task:** Implement real `verify_assertion(assertion, expected_challenge, credential_pubkey) → Result<()>` using the `webauthn-rs` crate (latest stable, v2.x). Verify: client data JSON origin, challenge, type ("webauthn.create" for registration, "webauthn.get" for assertion), signature over authenticator data + client data hash, counter > stored counter.
- **DoD:**
  - `verify_assertion` returns `Ok(())` for a valid assertion (use the RFC 8809 test vectors).
  - `verify_assertion` returns `Err` for: wrong challenge, wrong origin, wrong type, invalid signature, replayed counter.
  - 5 unit tests using RFC 8809 vectors.
- **Commit:** `feat(webauthn): real assertion verification with RFC 8809 test vectors`

### U3 (sub-agent): Phone enrollment + decide endpoints
- **File:** `gateway/src/routes/phone.rs`
- **Task:** Wire `POST /phone/enroll` to call U1's ceremony begin + accept the `AuthenticatorAttestationResponse`, verify it via U2, store the credential public key in the `credentials` table. Wire `POST /phone/decide` to accept an `AuthenticatorAssertionResponse` for session approval/denial — verify via U2, then call `approve_session` / `deny_session`.
- **DoD:**
  - `POST /phone/enroll` with a valid attestation → 200, credential stored.
  - `POST /phone/enroll` with an invalid attestation → 401.
  - `POST /phone/decide` with a valid assertion → session approved/denied in DB.
  - `POST /phone/decide` with an invalid assertion → 401.
  - Integration test: `test_full_webauthn_enrollment_and_decide`.
- **Commit:** `feat(webauthn): wire enrollment + decide endpoints with real verification`

### U4 (orchestrator-only): E2E test with real browser
- **Task:** Write `scripts/webauthn_e2e.sh` that uses a virtual authenticator (via `puppeteer` or `playwright` headless) to perform the full ceremony: begin → enroll → order → decide. Run it against the live gateway.
- **DoD:**
  - Script completes without manual intervention.
  - Audit log shows `webauthn_enrollment` + `webauthn_assertion` + `session_approved` events.
  - All events dual-signed (Ed25519 + ML-DSA-65).
- **Commit:** `test(webauthn): E2E enrollment + decide with virtual authenticator`

### Wave U DoD Gate (orchestrator-only)

## WAVE V: Workflow Engine — Real DAG Execution

**Goal:** The workflow engine currently marks runs as "running" but never
actually executes steps. Make it real: schedule pods, run step tasks, collect
results, advance the DAG, handle failures + retries.

**Context budget:** 5 sub-agent tasks.

### V1 (sub-agent): Step executor
- **File:** `gateway/src/workflow/executor.rs` (new)
- **Task:** Implement `execute_step(state, run_id, step) → Result<StepResult>` that: (1) calls `/agent/order` internally to schedule a pod for the step's image, (2) runs the step's `task` instruction via `stronghold_exec`, (3) collects stdout/stderr/exit_code, (4) calls `/agent/release`, (5) returns `StepResult { exit_code, stdout, stderr, duration_ms }`.
- **DoD:**
  - `execute_step` returns a `StepResult` for a simple `echo hello` task.
  - Pod is created + destroyed (no leak).
  - Audit entries written for `workflow_step_started` + `workflow_step_completed`.
  - Unit test with mocked scheduler.
- **Commit:** `feat(workflow): step executor — schedule pod, run task, collect result`

### V2 (sub-agent): DAG advancement
- **File:** `gateway/src/workflow/engine.rs`
- **Task:** Implement `advance_dag(state, run_id) → Result<()>` that: (1) reads the run's current step states, (2) finds steps whose `depends_on` are all `completed`, (3) calls `execute_step` for each (in parallel if independent), (4) updates step states, (5) evaluates `condition` expressions, (6) repeats until no more steps can run, (7) marks the run `completed` or `failed`.
- **DoD:**
  - A 2-step linear DAG (s1 → s2) executes both steps in order.
  - A 2-step parallel DAG (s1, s2 independent) executes concurrently.
  - A conditional DAG (`condition: "s1.result.exit_code == 0"`) skips s2 if s1 fails.
  - Run status transitions: `running` → `completed` (all steps pass) or `failed` (any step fails).
- **Commit:** `feat(workflow): DAG advancement — parallel steps, conditions, status transitions`

### V3 (sub-agent): Retry + timeout
- **File:** `gateway/src/workflow/engine.rs`
- **Task:** Add `max_retries` (default 0) and `timeout_secs` (default 3600) to `Step`. On step failure, retry up to `max_retries` times with exponential backoff (1s, 2s, 4s, ...). On timeout, kill the pod + mark step as `timed_out`.
- **DoD:**
  - A step with `max_retries: 2` that fails 2 times then succeeds → step status `completed`, retry_count=2.
  - A step with `timeout_secs: 5` that sleeps for 60s → step status `timed_out` after 5s.
  - Unit tests for retry logic + timeout.
- **Commit:** `feat(workflow): retry with exponential backoff + step timeout`

### V4 (sub-agent): Step SSE streaming
- **File:** `gateway/src/routes/workflows.rs`
- **Task:** Add `GET /workflow/run/:id/stream` SSE endpoint that emits events as the DAG advances: `step_started`, `step_completed`, `step_failed`, `step_retried`, `run_completed`, `run_failed`. Each event includes the step ID, result, and timestamp.
- **DoD:**
  - `curl -N /workflow/run/<id>/stream` emits events in real-time as the DAG runs.
  - Events are JSON-formatted with `event:` + `data:` SSE fields.
  - Connection closes after `run_completed` or `run_failed`.
- **Commit:** `feat(workflow): SSE stream for real-time DAG progress`

### V5 (orchestrator-only): E2E workflow test
- **Task:** Write `scripts/workflow_e2e.sh` that creates a 3-step DAG (plan → implement → test), runs it, streams events, and verifies all 3 steps complete. Run against the live gateway.
- **DoD:**
  - Script creates a workflow, starts a run, streams SSE events to stdout.
  - All 3 steps reach `completed`.
  - Run status = `completed`.
  - Audit log has `workflow_step_started` + `workflow_step_completed` × 3 + `workflow_run_completed`.
- **Commit:** `test(workflow): E2E 3-step DAG with SSE streaming`

### Wave V DoD Gate
- `cargo test --features no-sev-snp workflow` → all pass
- `bash scripts/workflow_e2e.sh` → exit 0

## WAVE W: Security Hardening

**Goal:** Close the known security gaps: rate limiting, anomaly scanner

**Context budget:** 4 sub-agent tasks.

- **File:** `gateway/src/middleware/rate_limit.rs` (new) + `gateway/src/routes/mod.rs`
- **Task:** Implement a token-bucket rate limiter (per-tenant, per-IP). Config: `max_requests_per_minute` (default 60). On exceeded, return 429 with `Retry-After` header. Apply to all `/agent/*` routes.
- **DoD:**
  - 100 rapid requests → first 60 succeed (200), next 40 get 429.
  - `Retry-After` header present on 429 responses.
  - Rate limit state is per-tenant (tenant A's limit doesn't affect tenant B).
  - Unit test: `test_rate_limit_per_tenant`.
- **Commit:** `feat(security): per-tenant token-bucket rate limiting (60 req/min)`

### W2 (sub-agent): E2E push encryption
- **File:** `gateway/src/push/ntfy.rs` + `gateway/src/push/e2e.rs`
- **Task:** Implement real E2E encryption for push notifications: X25519 + ML-KEM-768 hybrid KEM → AES-256-GCM. The phone's public keys (enrolled during WebAuthn) are used to encapsulate a symmetric key. The ntfy server sees only ciphertext. Remove the "plaintext fallback" warning.
- **DoD:**
  - `send_encrypted_notification_to` produces a base64 ciphertext that the ntfy server cannot read.
  - Decryption with the phone's private key recovers the plaintext.
  - Unit test with known key pairs: `test_e2e_encrypt_decrypt_roundtrip`.
  - No "PLAINTEXT notification" warnings in the gateway log.
- **Commit:** `feat(security): E2E push encryption (X25519 + ML-KEM-768 → AES-256-GCM)`

### W3 (sub-agent): Audit log tamper detection + alerting
- **File:** `gateway/src/audit/verify.rs` + `gateway/src/middleware/audit_check.rs` (new)
- **Task:** Add a background task that runs `verify_tenant` every 5 minutes for each tenant. If any entry fails verification (hash mismatch, bad signature, broken chain), emit a `security_alert` audit event + push a notification to the tenant's phone.
- **DoD:**
  - Tamper with one audit entry → within 5 minutes, `security_alert` event is logged.
  - Push notification sent to the tenant's phone.
  - The background task runs without blocking the main event loop.
- **Commit:** `feat(security): automated audit log tamper detection + alerting`

### W4 (sub-agent): Credential rotation
- **File:** `gateway/src/routes/credentials.rs` + `gateway/src/crypto/vault.rs`
- **Task:** Implement `POST /admin/credentials/:id/rotate` that: (1) decrypts the old value, (2) re-encrypts with a freshly-derived tenant key (rotating the HKDF salt), (3) updates the row, (4) emits a `credential_rotated` audit event. Also implement `POST /admin/keys/rotate-audit` + `POST /admin/keys/rotate-push` for rotating the master signing/encryption keys.
- **DoD:**
  - Rotate a credential → old value still decrypts correctly after rotation (re-encrypted with new key).
  - Rotate audit keys → new audit entries signed with new Ed25519 + ML-DSA-65 keys; old entries still verifiable with old keys (stored in a `retired_keys` table).
  - Audit event `credential_rotated` / `audit_keys_rotated` / `push_keys_rotated` emitted.
- **Commit:** `feat(security): credential + master key rotation with retired-key verification`

## COMMITS + PUSH CADENCE

- **Per task:** exactly one commit, conventional-commit format
  (`feat(scope): ...`, `fix(scope): ...`, `test(scope): ...`, `docs(scope): ...`)
- **Per wave:** one `git push origin main` after the DoD gate passes
- **Per wave:** one worklog entry with `Wave <letter>: PASS` or `Wave <letter>: FAIL (reason)`
- **Final:** `git tag v1.2.0` + `git push origin v1.2.0` + GitHub release

The orchestrator MUST NOT batch commits across waves. Each wave's push is
independent — if a later wave fails, the earlier waves' work is already
safely on `main` and tagged in the worklog.
