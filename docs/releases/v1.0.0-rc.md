# Stronghold v1.0.0-rc Release Notes

**Release Date:** 2026-09-15

> 🟢 **Release candidate — feature-complete for v1.0.**
>
> This release closes every roadmap item from
> [`v0.10.0-beta`](./v0.10.0-beta.md#roadmap-v10-rc). Stronghold now ships a
> structured **task model** that decouples *what to do* from *where it runs*,
> a **workflow engine** that executes DAGs of tasks with parallel steps,
> conditions, and retries, a **credential vault** with per-tenant
> AES-256-GCM encryption and pod-time env injection, a full **git flow**
> (clone → branch → commit → push → PR → status → log), an
> **agent-to-agent message bus** (post / poll / SSE), a **bash SDK** with 15
> high-level functions, and a **control channel** that delivers structured
> JSON to running agents over OSC 51 escape sequences — all without breaking
> the beta's WebAuthn approval flow, post-quantum transport, or dual-signed
> audit log.
>
> The phone PWA also gained a **Tasks** section that subscribes to per-task
> SSE streams and renders live status badges, durations, exit codes,
> summaries, the latest audited command, and workflow step indicators.

## Overview

Stronghold v1.0.0-rc is the third tagged release of a self-hosted gateway
that lets AI agents request, attach to, and work inside isolated containerd
workspaces on a fleet of Vultr boxes — with phone-approved sessions
(WebAuthn, no custom phone app), post-quantum cryptography end-to-end,
SEV-SNP confidential computing (code complete; untested on hardware), and
multi-tenancy from day one.

Where `v0.10.0-beta` shipped the secure substrate (TLS 1.3 hybrid PQ
transport, dual-signed audit log, E2E-encrypted push, anomaly scanning,
quorum enforcement, Prometheus metrics), `v1.0.0-rc` ships the **structured
work layer** on top of it: tasks, workflows, credentials, git, messaging,
and the SDK that ties them together. An agent with `bash` + `curl` (or the
SDK sourced) can now declare a task, watch it transition through its
lifecycle, fan out a DAG, pull secrets into env vars, commit work to a
branch, open a PR, and coordinate with peer agents — all through one
tenant-scoped bearer token.

## Features

### Task Model

A **task** is a structured work unit with a full lifecycle:
`queued → scheduled → running → completed | failed | cancelled`.

Tasks decouple *what to do* (the immutable **spec**: instruction, image,
TTL, context) from *where it runs* (the machine). A task is created in the
`queued` state; the scheduler (or an operator) later assigns it a machine
and starts it. Results are submitted back via a dedicated endpoint and
audited with `task_completed` / `task_failed` events.

| Method | Path                       | Purpose                              |
|--------|----------------------------|--------------------------------------|
| POST   | `/agent/task`              | Create a queued task                 |
| GET    | `/agent/task/:id`          | Fetch status, spec, result, timings  |
| POST   | `/agent/task/:id/result`   | Submit exit code + stdout + summary  |
| GET    | `/agent/task/:id/stream`   | SSE stream of status transitions     |

The SSE stream emits `task_created`, `task_started`, `task_completed`,
`task_failed`, `task_cancelled`, and `task_status` events (one per
lifecycle transition) with a `{task_id, status, result}` payload, plus a
30 s heartbeat. The stream closes automatically once the task reaches a
terminal state.

The phone PWA subscribes to this stream on every `session_started` event
and renders a live card per task (see [Phone PWA](#phone-pwa) below).

### Structured Exec

`POST /agent/:machine_id/exec` runs a non-interactive command in the
agent's pod and returns structured JSON: `{exit_code, stdout, stderr,
duration_ms, audit_seq}`. Unlike the raw PTY WebSocket, this endpoint is
for machine-parseable results — agents that want to check `cargo test`
output, parse `git status --porcelain`, or capture an exit code without
scraping a byte stream.

- **Auth:** `connect_token` query parameter (SHA-256 hashed and compared
  against `machines.connect_token_hash`), identical to the PTY endpoint.
- **Body:** `{cmd, args[], cwd?, timeout_secs, env{}}`.
- **Timeouts:** wall-clock `timeout_secs` → `504 Gateway Timeout`.
- **Audit:** every invocation is recorded as a `cmd_exec` event with
  `{cmd, exit_code, duration_ms}`; the audit sequence number is returned
  in the response so callers can correlate.

### Mid-Session Reprompt

`POST /agent/:machine_id/instruct` injects a new instruction into a
running session without re-approval. The original phone approval covers
the entire TTL — reprompts are delivery-only. Three modes:

| Mode      | Delivery                                                                              |
|-----------|---------------------------------------------------------------------------------------|
| `pty`     | Inject the instruction as a comment + text into the PTY stdin                         |
| `control` | Send a JSON envelope on the control channel via OSC 51 escape sequences (see below)   |
| `task`    | Queue a sub-task on the same machine (created with `status = 'queued'`)               |

Each reprompt carries a `priority` hint (`low` / `normal` / `high`) and is
audited as `instruct_received` with the mode, priority, and a 200-char
instruction snippet.

### Credential Vault

Encrypted storage for agent secrets (SSH keys, API tokens, env vars,
files). Uses **AES-256-GCM** with per-tenant keys derived via **HKDF-256**
from the audit Ed25519 secret key + `tenant_id`:

- **IKM** = Ed25519 secret key bytes (32 bytes)
- **salt** = `tenant_id` (UTF-8)
- **info** = `"stronghold-credential-vault-v1"`

The tenant key is derived in memory, **never stored**. Each credential
gets a fresh 12-byte random nonce per encryption.

| Method | Path                                          | Purpose                         |
|--------|-----------------------------------------------|---------------------------------|
| POST   | `/admin/credentials`                          | Create an encrypted credential  |
| GET    | `/admin/credentials`                          | List credentials (metadata)     |
| GET    | `/admin/credentials/:id`                      | Get one credential              |
| DELETE | `/admin/credentials/:id`                      | Delete a credential             |
| POST   | `/admin/credentials/:id/rotate`               | Rotate the plaintext value      |
| GET    | `/agent/:machine_id/credentials/:name`        | Decrypt + fetch at runtime      |

At pod creation time the scheduler decrypts the tenant's `env_var`
credentials and injects them as environment variables into the container,
so agents never see ciphertext and never need to call the vault at
runtime for env vars. SSH keys and API tokens are fetched on demand via
the agent endpoint.

### Git Flow

A seven-step git pipeline that runs inside the agent's pod via `kube
exec`. All operations are audited and SSH-token decryption is handled
server-side so the agent never sees the private key.

| Method | Path                                          | Purpose                                  |
|--------|-----------------------------------------------|------------------------------------------|
| POST   | `/agent/:machine_id/git/clone`               | Clone a repo (decrypts SSH token)        |
| POST   | `/agent/:machine_id/git/branch`              | Create + checkout a branch               |
| POST   | `/agent/:machine_id/git/commit`              | Stage + commit with a message            |
| POST   | `/agent/:machine_id/git/push`                | Push the current branch                  |
| POST   | `/agent/:machine_id/git/pr`                  | Open a pull request (GitHub API)         |
| GET    | `/agent/:machine_id/git/status`              | `git status --porcelain` as JSON         |
| GET    | `/agent/:machine_id/git/log`                 | Recent commits as JSON                   |

### Workflow Engine

A DAG executor that walks a workflow's directed acyclic graph and runs
each step as a Task.

- **DAG format:** JSON stored in `workflows.dag` —
  `{steps: [{id, task, image?, depends_on[], condition?, max_retries?}]}`.
- **Execution model:** find ready steps (deps all in `completed_steps`),
  partition into run vs. skip by condition, spawn one `tokio::task` per
  step, poll for terminal status, repeat.
- **Parallel steps:** steps whose dependencies are all met launch
  concurrently via `tokio::spawn`; the executor awaits the whole batch
  before re-evaluating the DAG.
- **Conditions:** simple `<path> <op> <value>` strings where `path` is a
  dot-separated lookup into per-step results (e.g.
  `build.result.exit_code == 0`), `op` is `==` or `!=`, and `value` is
  an integer, boolean, or quoted string.
- **Retries:** each step has its own `max_retries` (default 3); a failed
  step is retried until it succeeds or exhausts its budget, at which
  point the run is marked `failed`.
- **Step timeout:** 30 minutes per attempt.
- **Audit:** `workflow_completed` / `workflow_failed` events on run
  termination.

| Method | Path                          | Purpose                          |
|--------|-------------------------------|----------------------------------|
| POST   | `/workflow`                   | Define a workflow (draft)        |
| GET    | `/workflow/:id`               | Fetch a workflow definition      |
| GET    | `/workflow`                   | List workflows                   |
| POST   | `/workflow/:id/run`           | Start a run                      |
| GET    | `/workflow/run/:id`           | Poll run status + step arrays    |

### Agent Message Bus

Agent-to-agent communication backed by the `agent_messages` SQLite
table. A message has a `from_machine`, an optional `to_machine`
(`NULL` = broadcast), a `channel` string, and an arbitrary JSON `body`.

| Method | Path                                          | Purpose                         |
|--------|-----------------------------------------------|---------------------------------|
| POST   | `/agent/:machine_id/messages`                 | Post a message                  |
| GET    | `/agent/:machine_id/messages`                 | Poll for messages (filtered)    |
| GET    | `/agent/:machine_id/messages/stream`          | Live SSE stream of messages     |

All three endpoints require the machine's `connect_token` (same SHA-256
hash check as PTY / exec / git). The SSE stream long-polls the table and
yields new messages within 500 ms, with a 30 s heartbeat keepalive.

### Agent Bash SDK

`agent/stronghold-agent.sh` — a single sourced file that exposes 15
high-level functions for every gateway endpoint. No more hand-writing
`curl` commands.

```bash
source /path/to/stronghold-agent.sh
export STRONGHOLD_URL=https://gateway.example.com
export STRONGHOLD_TOKEN=<agent bearer token>

task_id=$(stronghold_task "build the crate" "stronghold/rust-nightly:2026.07" 3600 \
        | jq -r .task_id)
stronghold_exec "$machine_id" cargo 600 -- build --release
stronghold_result "$task_id" 0 "$stdout" "" "build ok"
```

| #  | Function                    | Wraps                                            |
|----|-----------------------------|--------------------------------------------------|
| 1  | `stronghold_task`           | `POST /agent/task`                               |
| 2  | `stronghold_result`         | `POST /agent/task/:id/result`                    |
| 3  | `stronghold_exec`           | `POST /agent/:machine_id/exec`                   |
| 4  | `stronghold_git_clone`      | `POST /agent/:machine_id/git/clone`              |
| 5  | `stronghold_git_branch`     | `POST /agent/:machine_id/git/branch`             |
| 6  | `stronghold_git_commit`     | `POST /agent/:machine_id/git/commit`             |
| 7  | `stronghold_git_push`       | `POST /agent/:machine_id/git/push`               |
| 8  | `stronghold_git_pr`         | `POST /agent/:machine_id/git/pr`                 |
| 9  | `stronghold_credential`     | `GET  /agent/:machine_id/credentials/:name`      |
| 10 | `stronghold_instruct`       | `POST /agent/:machine_id/instruct`               |
| 11 | `stronghold_shell`          | WebSocket PTY (`websocat`)                       |
| 12 | `stronghold_workflow_create`| `POST /workflow`                                 |
| 13 | `stronghold_workflow_run`   | `POST /workflow/:id/run`                         |
| 14 | `stronghold_workflow_status`| `GET  /workflow/run/:id`                         |
| 15 | `stronghold_help`           | Print usage for every function                   |

Every public function prints the gateway's JSON response on stdout and
returns the curl exit code, so callers can pipe to `jq` and check `$?`.

### Control Channel

The `control` mode of `/agent/:machine_id/instruct` delivers structured
JSON to a running agent without disturbing the PTY byte stream. It uses
**OSC 51** escape sequences:

```
\x1b]51;stronghold:control\x07{<JSON>}\x1b]51;stronghold:control\x07
```

The opening `\x1b]51;stronghold:control\x07` signals "control message
start"; the closing `\x1b]51;stronghold:control\x07` signals "control
message end". The bytes between are a JSON envelope:
`{type: "instruct", instruction, context, priority}`. Agents that
parse their PTY stream can extract these envelopes and act on them
without the noise of a comment-injected `pty`-mode reprompt.

### Shared PVC Workspaces

Each tenant gets a **per-tenant PersistentVolumeClaim** mounted into
every pod at a well-known path. Workspaces survive pod restarts and are
shared across all of a tenant's machines, so an agent can clone a repo
into the PVC on one machine and continue working on it from another
without re-cloning. The PVC is scoped to the tenant — cross-tenant
access is denied at the volume layer.

### Phone PWA

The phone enrollment PWA (`phone/enroll.html`) gains a **Tasks** section
that sits between Pending Approvals and Device. When a `session_started`
SSE event arrives, the phone:

1. Subscribes to `GET /agent/task/:id/stream` for each `task_id` in the
   payload.
2. Opens the audit WebSocket (`/agent/:machine_id/audit`) to surface the
   latest `cmd_exec` command in real time.
3. Renders a card per task showing:
   - **Instruction** (from the task spec)
   - **Status badge** — queued = gray, running = blue, completed =
     green, failed = red
   - **Duration** — from `started_at` to `finished_at` (client-side
     capture when server timestamps aren't available, so running tasks
     tick live)
   - **Exit code** and **summary** from the result
   - **Latest command** from the audit stream (`$ <cmd>`)
4. Renders a **workflow steps** list with ✅ / ⏳ / ❌ indicators when
   the session is part of a workflow run.

The section is fully additive — the existing enrollment, approval, and
revoke flows are unchanged. All fields degrade gracefully: if the
backend hasn't populated `task_ids` or `workflow_steps` in the
`session_started` payload yet, the section shows the empty-state
message and nothing breaks.

## Known Issues

- **WebAuthn PQC** — FIDO authenticators do not yet ship with
  post-quantum algorithms (~2027 expected). Hardware limitation; not
  fixable in software.
- **SEV-SNP on real hardware** — dev box lacks `/dev/sev`. Code
  compiles, key sealing tested with software keys. Hardware-blocked.
- **Per-token rate limiting** — implemented but the default bucket is
  generous; operators should tune per deployment.
- **Phone task monitoring** — the Tasks section relies on
  `session_started` SSE events carrying `task_id` / `task_ids`. Until
  the gateway emits these fields, the section shows the empty state.
  The task stream and audit WebSocket connections work independently of
  this.
